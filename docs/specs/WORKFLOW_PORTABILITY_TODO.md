# Workflow portability TODOs

**Requested by Patrick:** 2026-09-09. **Status:** backlog for scoping; no new implementation or external model calls authorized by this list.

**Goal:** Attune workflows can operate with Claude and at least one non-Claude model/backend, with explicit capability requirements and equivalent observable success/failure handling. Supporting two Claude model names alone does not establish this portability.

**Context and ownership:** During attune-rag Phase 1, the installed Attune spec runner invoked Claude-backed code-review and security-audit workflows. The initial calls failed DNS resolution, and automatic approval review rejected a network-enabled rerun without destination-specific authorization. Patrick chose Codex/local review instead. The observed coupling lives in Attune's workflow/runner layer; attune-ai is the expected implementation owner. This attune-rag backlog captures the cross-project request without adding it to Phase 1's five tasks. Inspect the actual installed and target-repository code versions before scoping changes.

- [ ] **Inventory model and backend assumptions.** Start with spec execution, code review, and security audit; enumerate other workflows using those components. Record hardcoded Claude SDK/CLI use, model identifiers, credential checks, tool schemas, structured output, and error handling. Cite implementation paths and distinguish model selection, provider selection, and execution host.
- [ ] **Define a capability matrix.** Compare Claude with at least one selected non-Claude backend. Cover text-only steps, repository/file tools, structured results, streaming, retries, cancellation, and task receipts. Mark supported, unsupported, and unverified behavior explicitly; do not describe a mock as a live integration.
- [ ] **Check explicit routing end to end.** The chosen backend must reach every workflow stage and nested review agent. A non-Claude selection must not launch Claude or require Claude credentials. Unsupported capabilities should fail with a useful explanation or follow an explicitly selected fallback policy.
- [ ] **Check credentials and external-access boundaries.** Each backend uses its own configuration. Missing credentials, rejected network access, and unavailable services produce distinguishable outcomes. No silent provider switch or unapproved code transfer is allowed.
- [ ] **Verify subscription versus API billing routes.** Patrick clarified that Claude itself is acceptable; the concern is separate API spend instead of subscription use. Verify the actual launcher/authentication route, remove API credentials for subscription-only execution, and prohibit fallback to paid API access. Report unavailable subscription authentication clearly. Record authentication evidence separately from any billing claim: a subscription login alone is not an invoice or overage receipt.
- [ ] **Create shared contract tests.** Run the same small repository fixture through each supported adapter using deterministic stubs first. Verify findings, severity, structured output validation, failure propagation, cancellation, and persisted receipts. Missing scores or malformed responses cannot become a passing review.
- [ ] **Validate actual integrations where authorized.** Run a bounded smoke test on Claude and the selected alternative, recording exact model/backend versions, configuration, tool access, and results. Require the same behavioral contract; findings and subjective scores need not be word-for-word identical. Keep live checks separately identified from offline tests.
- [ ] **Check local-only operation.** Workflows that can complete with static analysis and tests should expose that route directly. Identify where model judgment remains necessary; do not require a model API merely to run an otherwise local check.
- [ ] **Verify CI and documentation match support.** Add applicable offline adapter coverage to the workflow owner's CI, document backend selection and limitations, and include a runnable non-Claude example. Schedule or run live checks only under separately approved credentials, costs, and triggers.

**Done when:** The agreed workflow inventory and capability matrix are code-grounded; supported Claude/non-Claude routes satisfy shared contracts; authorized live receipts establish claimed integrations; missing credentials or unsupported features fail transparently; instructions accurately describe the working choices. Select exact workflows/backends and live-test bounds during later scoping.
